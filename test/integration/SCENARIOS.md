**이번 통합테스트로 찾아서 고친 버그 3건**

1. **nginx `/ai-service/` 가 항상 500** — `set` 이 `rewrite ... break` 아래에 있어 실행되지
   않았고 `proxy_pass http://` 가 되었다. 문법도 유효하고 컨테이너도 healthy 라
   `nginx -t` 나 `docker compose ps` 로는 안 드러난다. 백엔드는 내부망에서
   `http://ai:8000` 을 직접 부르므로 기능도 멀쩡해 보였다.
2. **AR 라이브에서 도안 로드 실패 → 인식·추적 전면 중단** — MinIO 공개 호스트에서 오는
   교차 출처 이미지를 `image.src` 로 바로 받아 캔버스가 오염됐고 `cv.imread` 가
   SecurityError 로 죽었다. 같은 문제를 이미 해결한 `loadImage` 가 `useBodyScan` 에
   있었지만 `ArLiveStage` 가 자체 구현을 따로 가지고 있어 그 수정을 못 받은 상태였다.
   구현을 `simulation/loadImage.ts` 한곳으로 합쳤다.
3. **차단한 사용자가 검색 결과에는 계속 노출** — 피드에는 차단 필터가 걸리지만 검색은
   Redis 인덱스에서 바로 가져오는 별도 경로라 필터가 빠져 있었다. 발견 후 수정 완료.

**결론: 서버 처리 능력은 병목이 아니다. 병목은 이미지 전송 대역폭 하나다.**

부하 최고점의 `docker stats` 에서 모든 컨테이너가 CPU 1% 미만이었다
(nginx 0.23%, backend 0.55%, postgres 0.00%, minio 0.07%, redis 0.54%,
메모리도 15.6GB 중 backend 794MB). 응답이 4초씩 걸리는데 서버는 놀고 있었다.
이미지만 빼면 100명이 30명보다도 빨라진다(339ms < 409ms).

측정된 대역폭 상한은 약 1.4 MB/s(≈11 Mbps)다. EC2 는 가장 작은 인스턴스도 이보다
훨씬 넓으므로 **부하를 건 PC 회선이 먼저 막힌 것**으로 보인다. 실제 사용자들이 각자 다른
회선을 쓴다면 이 병목은 재현되지 않는다. 다만 **발표장에서 관객이 같은 와이파이를
공유하면 재현될 수 있다** — 그 와이파이가 이 테스트의 PC 회선과 같은 역할을 한다.

**개선 방향** (발표 전 필수는 아님): 업로드된 원본을 그대로 내려주고 있고 리사이즈·
썸네일 코드가 없다. 로그에 11.6MB 짜리 이미지도 보인다. 피드용 썸네일(예: 폭 600px)만
만들어도 전송량이 5~10 배 줄고, WebP 변환이나 CDN 을 얹으면 더 줄일 수 있다.

**발표 자료용 수치**

### 🔴 B-1. 노트북 AI 서버 끊김 (노트북 담당자 필요, 15분)

AI 생성은 EC2 가 아니라 **노트북 + SSH 역터널**에 의존한다(`ai-api` 서비스는
`profiles: ["aws-ai-fallback"]` 이라 평소 뜨지 않고, `laptop-ai-relay` 가 `ai-api` 라는
이름을 가로채 노트북으로 넘긴다). 노트북이 절전에 들어가거나 와이파이가 끊기면
AI 기능 전체가 죽는다. **발표 중 절전 한 번으로도 일어난다.**

- [x] 노트북 AI 서버를 끄고 도안 생성 요청 → **"생성할 수 없습니다" 안내. 무한 로딩 아님 ✅**
- [ ] **생성 도중** 터널 끊기 → 사용자 화면이 어떻게 되는가 ← **남은 항목. 위와 경로가 다르다**
- [ ] 노트북 복구 후 자동으로 다시 되는가

> 위 두 경우는 다른 경로다. 버튼을 누르는 시점에 이미 끊겨 있으면 연결 실패를 곧바로
> 알 수 있어 에러를 띄울 수 있다. 그런데 **요청이 이미 서버로 넘어간 뒤** 끊기면
> 백엔드는 응답을 기다리게 되고, 그 대기 한도가 `AI_GENERATION_TIMEOUT=60m` 이다.
> 60분 로딩 위험은 이쪽에 남아 있다.

> `AI_GENERATION_TIMEOUT=60m` 이다. **사용자가 최대 한 시간 로딩 화면에 갇힐 수 있다.**
> 이 시나리오의 핵심 확인 사항이다.

터널 상태 확인:
```bash
curl -s -m 5 http://127.0.0.1:18000/health
docker logs starttoo-laptop-ai-relay --tail 20
```

## 3. 결론 난 사항 (재논의 불필요)

발견했지만 **고치지 않기로 했거나 이미 팀이 아는** 것들. 다시 발견하더라도 다시 논의하지 말 것.

| 사항 | 상태 |
|---|---|
| 게시물 검색이 관련 없는 주제로 폴백 (`타투`→나무, `로고`→곰) | **현행 유지 결정** |
| FCM 푸시 | **하지 않기로 결정** |
| 동시 생성 요청 시 대기 안내 없음 | **시연자가 말로 안내** |

**게시물 검색 폴백** — 검색은 질의를 주제(subject)에 매칭하는데
`exact → prefix → fuzzy1 → fuzzy2 → contains` 순으로 내려가며 **항상 하나를 고른다.**
한글 2글자는 자모 4개라 편집거리 2면 거의 아무거나 걸린다. 설계상 트레이드오프이고
팀에서 허용 가능한 동작으로 판단했다.

**FCM 푸시** — 프론트엔드에 `firebase` 의존성·서비스워커·`Notification.requestPermission()`
이 모두 없고 `/v1/devices` 로 기기 토큰을 등록하는 호출도 없다. 백엔드는
`DeviceController`·`PushDeliveryListener`·`FIREBASE_ENABLED` 까지 갖춰져 있지만
등록하는 쪽이 없어 보낼 대상이 생기지 않는다. 알림은 인앱 경로로만 제공한다.
백엔드 코드·설정은 남겨두되 사용하지 않는다.

**동시 생성 대기 안내** — 추론 슬롯이 전역 1개라 순차 처리되는 것 자체는 정상인데,
두 번째 화면에는 평소와 같은 로딩만 뜬다. 진짜 대기 표시를 하려면 백엔드가 큐 상태를
내려줘야 해서 지금 고칠 일이 아니다. 여유가 있으면 로딩 문구에
"다른 요청이 있으면 순서대로 처리됩니다" 한 줄을 덧붙이는 정도가 비용 대비 효과가 좋다.

## 4. 남아 있는 리스크 (아직 판단 안 됨)

- **AR 이 외부 CDN 에 의존한다.** 인식 모델과 WASM 을 전부 `cdn.jsdelivr.net`,
  `storage.googleapis.com` 에서 받는다. **발표장 네트워크가 이 두 도메인을 막으면
  AR 이 통째로 죽는다.** 현장 와이파이로 반드시 미리 확인할 것.
- **MediaPipe WASM 버전 불일치.** 설치된 `@mediapipe/tasks-vision` 은 0.10.35 인데
  `inkproof/engine.ts` 는 CDN 에서 0.10.14 를 받는다(`image-engine.ts` 는 0.10.35 로
  맞춰져 있다). AR 장애의 원인은 아니었지만 어긋난 상태다.
- **WebSocket 은 연결 시 한 번만 토큰을 검사한다.** 연결된 세션은 토큰이 만료돼도
  유지되지만, 그 상태에서 연결이 끊기면 만료된 토큰으로 5초마다 무한 재시도하고
  스스로 복구하지 못한다(화면을 조작해 HTTP 요청이 나가면 복구됨).
  **시연 직전 새로고침 한 번**이 예방책이다.

## 5. 발표 전 정리 목록

- [ ] **Jenkins 8082 외부 노출 차단** — 현재 인터넷 전체에 공개돼 있고 평문 HTTP 다.
      Jenkins 는 `/var/run/docker.sock` 접근 권한(사실상 root)과 `.env` 전체를
      크리덴셜로 들고 있다. 단 `ufw deny 8082` 는 안 먹을 수 있다 — Docker 가 iptables 를
      직접 조작해 UFW 를 우회하므로, 포트 바인딩을 `127.0.0.1:8082` 로 바꾸는 편이 확실하다.
      막은 뒤에도 SSH 터널로는 계속 접속된다.
- [ ] 테스트로 남은 MinIO 이미지 정리 (`imageSeq 10015, 10016, 10018`)

## 6. 자동 검사

```bash
bash test/integration/smoke.sh      # 인프라 도달성 13개
bash test/integration/api-flow.sh   # API 플로우 32개
```

인증·쓰기 구간까지 돌리려면 토큰이 필요하다. 콘솔에서:
```js
copy(JSON.parse(localStorage.getItem("starttoo-auth")).state.accessToken)
```
Git Bash 에서:
```bash
read -r TOKEN && export TOKEN && printf '길이=%s\n' "${#TOKEN}"   # 붙여넣고 Enter (300~900자면 정상)
WRITE=1 bash test/integration/api-flow.sh
```

`WRITE=1` 은 **운영 서버에 실제 게시물을 만든다.** 확인 후 자동 삭제되지만 공개 피드에
잠깐 노출되고 AI 분류도 실제로 돈다. 업로드된 이미지는 남는다(이미지 삭제 API 가 없다).

**결과: 18개 항목 전부 차단, FAIL 0.**

| 구간 | 결과 |
|---|---|
| 토큰 없이 게시물 생성 · 내 정보 · DM 목록 · 알림 | 전부 401 |
| 서명 변조 토큰 | 전부 401 |
| B 가 A 게시물 수정 / 삭제 | 403 |
| B 가 A 의 imageSeq 로 게시물 생성 | 404 (존재 자체를 감춤) |
| B 가 A 의 DM 조회 / 전송 / 읽음처리 / 방삭제 | 전부 403 |
| **대조군** — A 가 자기 게시물 수정 | **200** (과차단 아님) |

판정 기준은 "정확히 403"이 아니라 **"성공하면 안 된다"**로 잡았다. 404 로 존재를 감추는 것도
올바른 구현이라 401/403/404 를 통과로 본다. 실제 사용자 데이터를 건드리지 않도록 A 계정이
일회용 게시물을 만들고 B 가 그것을 공격하는 구조이며, 끝에서 지운다.

**아직 안 본 인가 표면**: 컬렉션(A 계정에 데이터가 없어 SKIP), 댓글 수정·삭제,
AR 세션 토큰으로 남의 세션에 업로드. 필요하면 `authz.sh` 에 같은 형식으로 추가하면 된다.

## 7. 테스트 규칙

지키지 않으면 결과가 오염된다. 아래 1번은 실제로 **없는 버그를 40분 쫓게 만들었다.**

1. **테스트 중에는 머지·배포 금지.** 배포는 컨테이너를 재생성해서 WebSocket 세션을 전부
   끊고 `docker logs` 기록도 지운다. 그러면 클라이언트가 5초마다 재연결하는 모습이
   "무한 루프 버그"처럼 보이는데, 원인을 확인할 로그는 이미 지워진 뒤다.
   불가피하게 배포했으면 **시각을 팀 채팅에 남긴다.**
2. 배포 직후라면 **5분 기다린 뒤** 시작한다.
3. 로그를 해석하기 전에 **배포 시각부터 확인한다.**
   ```bash
   docker inspect starttoo-backend --format 'created={{.Created}} started={{.State.StartedAt}} restarts={{.RestartCount}} oom={{.State.OOMKilled}}'
   ```
   `created` ≈ `started` 이고 `restarts=0` 이면 크래시가 아니라 **배포**다.
4. **실제 배포 도메인 + 실제 모바일 기기**로 한다. 로컬에서 통과하고 배포에서 깨지는 것이
   이 프로젝트의 주된 사고 패턴이다.
5. **테스트 도구 자체를 먼저 의심한다.** 실패가 나오면 "서버가 이상하다"보다
   "내 요청이 서버에 온전히 도달했나"를 먼저 본다. 이번에도 한글 게시물 실패가
   서버 버그가 아니라 Git Bash 의 인자 인코딩 문제였다(본문을 파일로 넘겨 해결).

## 8. 기록 방법

- 체크박스에 결과를 적고, 실패는 **재현 절차 + 기기/브라우저 + 시각**을 남긴다.
- 시각이 있어야 서버 로그와 대조할 수 있다. 그 시간대에 배포가 있었는지 7번 3항으로 확인한다.
