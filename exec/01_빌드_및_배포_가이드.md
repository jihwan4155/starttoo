## 1. 시스템 구성

전체 스택은 **EC2 1대에서 Docker Compose 단일 스택**으로 동작한다. 별도의 WAS 제품(Tomcat 설치본,
WebLogic 등)은 사용하지 않고, Spring Boot 내장 Tomcat + 리버스 프록시(nginx) 구성이다.

```
                 [ 인터넷 ]
                     │  443/80
             ┌───────▼────────┐
             │  nginx (호스트) │  starttoo-nginx  ← Let's Encrypt 인증서
             └───┬───┬────┬───┘
     /  (SPA)    │   │    │   /ai-service/  (커버업 검색)
                 │   │    └────────────────► ai        :8000
   /v1/, /ws,    │   └─────────────────────► backend   :8080 ──► postgres :5432
   /actuator/,   │                                      ├──────► redis    :6379
   /swagger-ui   │                                      ├──────► minio    :9000
                 └─────────────────────────► frontend  :80     └──► ai-api :8000 (relay)
```

| 역할 | 컨테이너 | 이미지 / 베이스 | 노출 |
|---|---|---|---|
| 리버스 프록시 | `starttoo-nginx` | `nginx:1.27-alpine` | 80, 443 (공개) |
| 프론트엔드(SPA 정적 서빙) | `starttoo-frontend` | `nginx:1.27-alpine` (빌드: `node:20-alpine`) | 내부 80 |
| 백엔드 API | `starttoo-backend` | `eclipse-temurin:21-jre-jammy` (빌드: `21-jdk-jammy`) | 내부 8080 |
| 커버업 도안 검색 엔진 | `starttoo-ai` | `python:3.11-slim` | 내부 8000 |
| AI 추론 API (생성/추출/분류) | `starttoo-ai-api` *(profile: `aws-ai-fallback`)* | `python:3.11-slim` | 내부 8000 |
| AI 릴레이 (외부 GPU 머신 연결) | `starttoo-laptop-ai-relay`, `starttoo-laptop-ai-host-relay` | `alpine:3.22` + `socat` | 내부 8000 (alias `ai-api`) |
| DB | `starttoo-postgres` | `postgres:16-alpine` | `127.0.0.1:5432` (loopback 전용) |
| 캐시/세션/검색 | `starttoo-redis` | `redis/redis-stack-server:latest` | 내부 6379 |
| 오브젝트 스토리지 | `starttoo-minio` | `quay.io/minio/minio:latest` | `127.0.0.1:9000`, `127.0.0.1:9001` (loopback 전용) |
| CI/CD | `jenkins` | `jenkins/jenkins:lts` + Docker CLI | `8082:8080` |

> Postgres와 MinIO는 `0.0.0.0`이 아니라 `127.0.0.1`에만 바인딩한다. 외부에서 직접 접속하려면
> SSH 터널을 뚫어야 한다. MinIO 오브젝트는 nginx의 `starttoo-storage.duckdns.org` 가상호스트로만
> 공개되고, MinIO 콘솔(9001)은 외부에 열려 있지 않다.

## 3. 클론부터 로컬 실행까지

```bash
git clone <GitLab 저장소 URL> S15P11D201
cd S15P11D201
cp .env.example .env      # 값 채우기 (5장 참고)
```

### 3.1 전체 스택을 Docker로 (권장)

```bash
docker compose --env-file .env up -d --build
```

- 접속: http://localhost (nginx), API `http://localhost/v1/...`
- `ai-api`는 `aws-ai-fallback` 프로필에 묶여 있어 기본 `up`에서는 뜨지 않는다. 띄우려면:

```bash
docker compose --profile aws-ai-fallback up -d ai-api
```

### 3.2 백엔드만 로컬 실행

```bash
cd backend
./gradlew bootRun --args='--spring.profiles.active=local'
```

- `local` 프로필은 Firebase·AI를 끄고 Swagger를 켠다(`application-local.yml`).
- Postgres/Redis/MinIO는 compose로 먼저 띄워 둔다:
  `docker compose up -d postgres redis minio`
- 테스트: `./gradlew test` — Testcontainers(PostgreSQL)를 쓰므로 **로컬에 Docker 데몬이 필요**하다.

### 3.3 프론트엔드만 로컬 실행

```bash
cd frontend
npm ci --legacy-peer-deps
npm run dev          # https://localhost:5173 (자체 서명 인증서)
npm run dev:http     # http://localhost:5174 (인앱 브라우저 등 인증서 신뢰 불가 환경용)
```

- 개발 서버는 `0.0.0.0` 바인딩이라 같은 와이파이의 휴대폰에서 PC LAN IP로 접속할 수 있다.
- 카메라(`getUserMedia`)와 카카오 SDK는 보안 컨텍스트가 필요하므로 평소에는 HTTPS 모드(`npm run dev`)를 쓴다.
- 프록시(`vite.config.ts`)
  - `/v1`, `/ws` → `VITE_API_PROXY_TARGET` (기본 `http://localhost:8080`)
  - `/ai-service` → `VITE_AI_PROXY_TARGET` (없으면 API 타깃)
  - 배포 백엔드를 볼 때도 CORS 때문에 **반드시 이 프록시를 거쳐야 한다**(브라우저 직접 호출은 403).
- 프론트 전용 로컬 값은 `frontend/.env.local`에 둔다:
  `VITE_KAKAO_JS_KEY`, `VITE_GOOGLE_CLIENT_ID`, (선택) `VITE_API_PROXY_TARGET`, `VITE_AI_PROXY_TARGET`

## 4. CI/CD (Jenkins) 배포

- Jenkins: 배포 서버의 `jenkins` 컨테이너, 호스트 포트 **8082**
- 파이프라인 정의: 저장소 루트 `Jenkinsfile`
- 트리거: GitLab webhook (`dev` 브랜치 기준)

### 4.1 파이프라인 단계

| 단계 | 내용 |
|---|---|
| Build | `docker compose --env-file "$ENV_FILE" build` |
| Deploy | 레거시 릴레이 컨테이너 정리 → `docker compose down --remove-orphans` → `COMPOSE_PARALLEL_LIMIT=1 docker compose up -d --remove-orphans` |

- `COMPOSE_PROJECT_NAME=s15p11d201`로 고정 — 수동 `docker compose up`과 같은 프로젝트로 인식되게 한다.
- `disableConcurrentBuilds()` — Deploy가 스택 전체를 down/up 하므로 동시 빌드는 반드시 깨진다.
  (실제로 빌드 92·93이 겹쳐 nginx가 못 뜨고 서비스가 중단된 사고가 있었다.)
- **테스트 스테이지는 없다.** 테스트는 로컬에서만 돌린다.

### 4.2 Jenkins Credentials

| ID | 종류 | 용도 |
|---|---|---|
| `starttoo-env-file` | Secret file | Compose에 넘길 `.env` 파일 전체 (모든 시크릿) |

환경변수를 바꾸려면 Jenkins의 이 Credential 파일을 교체한 뒤 재빌드해야 한다. 저장소에는 `.env`가
커밋되지 않는다(`.gitignore`).

### 4.3 수동 배포

```bash
ssh -i <키> ubuntu@i15d201.p.ssafy.io
cd ~/S15P11D201
docker compose --env-file .env up -d --build
```

| `AI_INTERNAL_TOKEN` | backend ↔ AI 추론 API 공유 토큰 | |

### 5.4 프론트엔드 빌드 인자 (중요)

Vite는 **빌드 시점에 값을 번들로 치환**한다. 런타임 `environment:`로는 주입되지 않으므로,
아래 두 값은 반드시 Compose `build.args`로 넘어가야 한다(`docker-compose.yml`에 이미 배선돼 있다).

| 빌드 인자 | 설명 |
|---|---|
| `VITE_KAKAO_JS_KEY` | 카카오 JavaScript 앱 키 (브라우저 노출이 정상) |
| `VITE_GOOGLE_CLIENT_ID` | 구글 OAuth 클라이언트 ID (브라우저 노출이 정상) |
| `VITE_API_BASE_URL` | 기본값 `/v1`. nginx가 같은 origin으로 프록시하므로 상대경로를 쓴다 |

> 이 값을 바꾸면 `docker compose up -d`만으로는 반영되지 않는다. **프론트엔드 이미지를 다시 빌드**해야 한다.

### 5.5 튜닝 값 (기본값으로 두어도 동작)

- AI 배치 분류: `AI_BATCH_TIMEOUT_PER_IMAGE=45s`, `AI_BATCH_TIMEOUT_OVERHEAD=10s`
  — 운영 서버에 GPU가 없어 CPU 추론이 이미지 1장당 약 23초다. 부하를 감안해 두 배로 잡았다.
- 분류 백필: `AI_CLASSIFICATION_BACKFILL_CRON=0 */5 * * * *`, `AI_CLASSIFICATION_MAX_ATTEMPTS=5`,
  `AI_CLASSIFICATION_RETRY_DELAY=5m` (재시도 창 약 25분)
- 커버업 색인 동기화: `COVERUP_INDEX_SYNC_CRON=0 */10 * * * *`, `COVERUP_STAGE1=auto`, `COVERUP_MAX_CONCURRENT=3`
- 추론 슬롯 대기: `INFERENCE_WAIT_TIMEOUT_SECONDS=120` (전역 슬롯 1개, 대기는 정상 상태)
- 업로드 상한: `MAX_IMAGE_BYTES=15728640`(15MB), `MAX_UPLOAD_MB=20`, nginx `client_max_body_size 100m`

## 6. DB 접속 정보 및 계정

### 6.1 PostgreSQL (운영)

| 항목 | 값 |
|---|---|
| 호스트(컨테이너 내부) | `postgres:5432` |
| 호스트(서버 로컬) | `127.0.0.1:5432` — **loopback 전용, 외부 직접 접속 불가** |
| 데이터베이스 | `starttoo` |
| 사용자 | `starttoo` |
| 비밀번호 | `POSTGRES_PASSWORD` — 실제 값은 `.env` 참조 (7장) |
| JDBC URL | `jdbc:postgresql://postgres:5432/starttoo` |
| 커넥션 풀 | HikariCP, max 20 / min idle 5 |

외부에서 접속하려면 SSH 터널을 연다:

```bash
ssh -i <키> -L 5432:127.0.0.1:5432 ubuntu@i15d201.p.ssafy.io
```

서버에서 바로 조회할 때는 컨테이너 자신의 env를 쓰는 편이 안전하다:

```bash
docker compose exec -T postgres sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "\dt"'
```

## 9. 배포 시 특이사항

1. **AI 추론은 배포 서버에서 돌지 않는다.**
   운영 서버에는 GPU가 없다. `ai-api` 서비스는 `aws-ai-fallback` 프로필로 묶여 평소에는 뜨지 않고,
   대신 `laptop-ai-relay` 컨테이너가 `ai-api`라는 **네트워크 alias**를 차지한다.
   경로: `backend → ai-api:8000` → `laptop-ai-relay`(socat) → `172.19.0.1:18001`
   → `laptop-ai-host-relay`(host network) → `127.0.0.1:18000` → **팀원 GPU 머신의 SSH 역터널**.
   - GPU 머신이 꺼져 있으면 `starttoo-laptop-ai-relay`가 `unhealthy`가 되고 AI 생성/추출이 실패한다.
     스택 자체는 정상 동작한다.
   - CPU 폴백으로 돌리려면 릴레이를 내리고 `docker compose --profile aws-ai-fallback up -d ai-api`로 전환한다.

2. **컨테이너가 healthy여도 AI 기능은 죽어 있을 수 있다.**
   `ai-api`의 헬스체크는 서버 응답만 확인한다(모델 로딩 실패로 unhealthy를 내면 nginx가
   기다리다 사이트 전체가 안 뜨기 때문). 모델 상태는 `/health`의 `status`·`classifier_status`로 본다.

3. **Compose 배포는 down → up이다.** 배포 중 수십 초 다운타임이 있고, 동시 빌드는 반드시 깨진다
   (`disableConcurrentBuilds()`로 큐잉).

4. **서버는 git 커밋이 아니라 워킹 트리로 빌드한다.** 서버에서 직접 수정한 파일은 커밋되지 않아도
   배포에 반영된다. 반대로 서버 워킹 트리가 더러우면 예상과 다른 것이 배포될 수 있다.

5. **TLS 인증서는 호스트의 `/etc/letsencrypt`를 읽기 전용 마운트한다.**
   컨테이너를 새로 만들어도 인증서는 호스트에 남는다. 갱신은 호스트의 certbot 담당.
   3개 도메인 각각 인증서가 있어야 nginx가 뜬다.

6. **`SPRING_JPA_HIBERNATE_DDL_AUTO=validate`.** 엔티티만 바꾸고 마이그레이션을 안 쓰면 백엔드가
   기동에 실패한다. 스키마 변경은 반드시 `V<n>__*.sql`을 추가한다.

7. **볼륨을 지우면 안 되는 것들**
   - `postgres-data`, `minio-data`, `redis-data` — 서비스 데이터
   - `ai-store` — 커버업 특징 파일(도안당 18KB). 지우면 전체 재색인 필요
   - `ai-siglip` — SigLIP2 가중치(약 1.7GB). 지우면 배포마다 HuggingFace에서 다시 받는다
   `docker compose down`은 볼륨을 지우지 않는다. **`down -v`는 절대 쓰지 않는다.**

8. **Docker 네트워크가 `172.19.0.0/16`으로 고정돼 있다.** UFW 규칙이 재배포마다 바뀌는
   `br-<id>` 이름에 묶이지 않도록 브리지 이름을 `starttoo-br`로 고정했다. 이 서브넷을 바꾸면
   릴레이의 게이트웨이 주소(`172.19.0.1`)와 방화벽 규칙을 함께 고쳐야 한다.

9. **커버업 엔진 워커를 늘리지 않는다.** 특징 파일 쓰기가 단일 프로세스여야 한다
   (두 워커가 같은 파일에 동시 append하면 스토어가 깨진다).

10. **nginx `/ai-service/`는 공개 경로다.** `COVERUP_INTERNAL_TOKEN`이 비어 있으면 누구나 검색을
    호출할 수 있고 CPU가 무제한으로 소모된다. 운영에서는 반드시 채운다.

11. **Firebase 키는 커밋하지 않는다.** `FIREBASE_SECRETS_DIR`(기본 `./secrets`)를 디렉터리 단위로
    마운트한다. 파일 단위로 마운트하면 파일이 없을 때 Docker가 그 경로에 빈 디렉터리를 만들어 버린다.

12. **문자 인증은 실제로 하지 않는다.** SMS 발송 비용 문제로 고정 코드(`1111`)를 쓰는 화면 전용
    장치다. `SMS_WEBHOOK_URL`·`SMS_API_KEY`는 비어 있다.

13. **Jenkins의 `DOCKER_GID`는 호스트의 docker 그룹 GID와 같아야 한다.** 현 서버 기준 113.
    다른 서버로 옮기면 `getent group docker`로 다시 확인해 이미지를 다시 빌드한다.

## 10. 배포 확인 체크리스트

```bash
# 1. 컨테이너 상태
docker compose ps

# 2. 백엔드
curl -sf https://starttoo.duckdns.org/actuator/health

# 3. 커버업 엔진 (ready=true 여야 정상)
docker compose exec -T ai python -c \
  "import json,urllib.request as u; print(json.load(u.urlopen('http://localhost:8000/health')))"

# 4. AI 추론 API (릴레이 경유)
docker compose exec -T backend curl -sf http://ai-api:8000/health

# 5. DB
docker compose exec -T postgres sh -c 'pg_isready -U "$POSTGRES_USER" -d "$POSTGRES_DB"'

# 6. 프론트
curl -sf -o /dev/null -w '%{http_code}\n' https://starttoo.duckdns.org/
```
